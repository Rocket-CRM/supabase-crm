| 5.3.6 ออกแบบการเชื่อมต่อระบบ (Integration Scope) และกาหนดการเชื่อมต่อระบบ (API Interface Document) สาหรับระบบ EEC OSS | Jointly scoped API Interface Document; OSS status on case | Equal | Proposal 5.5 |
| 5.3.7 จัดทาเอกสารแสดงรายละเอียดคุณสมบัติของโครงสร้างพื้นฐาน ประกอบด้วย ระบบฐานข้อมูล (Database) เครือข่าย (Network) และสถาปัตยกรรมระบบ (System Architecture) พร้อมทั้งกาหนดคุณสมบัติขั้นต่าของโครงสร้างพื้นฐานที่ผู้ว่าจ้างต้องจัดเตรียมให้เพียงพอต่อการใช้งานในวงกว้าง (Production) โดย สกพอ. จะประสานงานกับผู้ให้บริการ Cloud เช่น GDCC เพื่อจัดหาเครื่องแม่ข่ายต่อไป | Vendor-agnostic min specs (DB/network/architecture) + install/config on buyer-provided hosts | Equal | Proposal 3, 4, 6 |
| 5.4 การประเมินความเสี่ยง ผลกระทบ และการปรับปรุงแก้ไขเพื่อรองรับการทางานร่วมกับระบบต่าง ๆ ภายในของ สกพอ. ที่เกี่ยวข้อง เช่น ระบบบริการ EEC OSS ซึ่งให้บริการด้านเขตส่งเสริมเศรษฐกิจพิเศษ ด้านสิทธิประโยชน์ ด้านอนุมัติ อนุญาต และด้านการให้คาปรึกษา เป็นต้น | Phase 1 risk note | Equal | Proposal 5.5, 6 |
| 5.5.1 การรับ/ป้อนข้อมูล (Data Capture) — 1) …รองรับการบันทึกแหล่งข้อมูลที่ได้รับมาจากหลากหลายช่องทาง เช่น โซเชียลมีเดีย (LINE OA, Facebook Messenger) อีเมล และ Call Center เป็นต้น 2) รองรับการนาเข้าและส่งออกข้อมูลจานวนมาก (Bulk Upload) ผ่านไฟล์มาตรฐาน เช่น CSV, Excel พร้อมระบบตรวจสอบความถูกต้องของข้อมูลเบื้องต้น (Data Validation) | Channel-tagged intake; bulk import with validation grid | Equal | Proposal 5.1 |
| 5.5.2 การจัดเก็บและบริหารข้อมูล (Data Management) — 1) หน้าจอแสดงข้อมูลลูกค้าแบบศูนย์รวม (Single Source of Truth) … 2) …ชุดข้อมูล (Master Data) … 3) …ระบบให้คะแนน (Lead Scoring) … 4) รองรับการตรวจสอบและจัดการข้อมูลซ้าซ้อนโดยอัตโนมัติ … 5) …บันทึกประวัติการให้ความยินยอม (Consent) …ตาม พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล | Customer 360; masters; score; Tax ID/name dedupe; consent history — **plus** guided duplicate-merge workspace | Better | Proposal 5.1, 9 |
| 5.5.3 การบริหารความสัมพันธ์ (Relationship & Activity Management) — 1) สามารถบันทึกปฏิสัมพันธ์การให้บริการ ติดตาม และกิจกรรมที่เกี่ยวข้องกับนักลงทุน (Interaction & Activity Tracking) … Timeline … รองรับการใช้งานผ่านอุปกรณ์พกพา (Mobile/Tablet) … 2) ระบบจัดการงานและปฏิทินนัดหมาย (Task & Calendar Management) … 3) ระบบออกเลขรับเรื่อง (Ticket Management) … SLA Tracking … Escalate … | Log activity; calendar tasks; ticket route/SLA/escalate — **plus** offline-tolerant field capture and configurable bureau escalation matrix | Better | Proposal 5.2, 9 |
| 5.5.4 การติดตามสถานะ (Pipeline / Workflow Management) — 1) ระบบต้องสามารถติดตามสถานะของนักลงทุน หรือโครงการลงทุน ในรูปแบบ Pipeline หรือ Workflow โดยสามารถกาหนดขั้นตอน (Stage) และเงื่อนไขการเปลี่ยนสถานะได้ รวมถึงสามารถแสดงความคืบหน้าของแต่ละรายการได้อย่างชัดเจน 2) รองรับ ระบบติดตามและแจ้งเตือนระยะเวลามาตรฐานการให้บริการ (Service Level Agreement) | Open case; move stage; checklist gate; stage SLA; pipeline board — **plus** journey template library (FDI / domestic / aftercare) | Better | Proposal 5.3, 9 |
| 5.5.5 รายงานและวิเคราะห์ (Reporting & Analytics) — 1) ระบบต้องสามารถจัด ท ารายงานและวิเคราะห์ข้อมูล (Reporting & Analytics) โดยรองรับการแสดงผลในรูปแบบ Dashboard และสามารถปรับแต่งรายงานได้ เช่น รายงานตามประเทศ อุตสาหกรรม มูลค่าการลงทุน เป็นต้น 2) สามารถส่งออกข้อมูลในรูปแบบ excel หรือ PDF ได้เป็นอย่างน้อย เป็นต้น | Native dashboards; exports — **plus** scheduled executive digests | Better | Proposal 5.4, 9 |
| 5.5.6 การเชื่อมโยงข้อมูล (Integration & Data Sharing) — 1) ระบบต้องสามารถเชื่อมโยงและแลกเปลี่ยนข้อมูลกับระบบอื่น (System Integration) ผ่าน API … โดยเชื่อมกับระบบ SSO EECO และ EEC OSS ของ สกพอ. เป็นต้น 2) รองรับการเชื่อมต่อข้อมูลผ่าน Open API (RESTful API / SOAP) เพื่อความยืดหยุ่นในการขยายระบบในอนาคต | SSO login; OSS pull on case; REST primary | Equal | Proposal 5.5 |
| 5.6.1 การกรองข้อมูล (Data Filtering): ระบบต้องสามารถแสดงผลภาพรวมภาระงาน (Heat Map) และต้องสามารถกรองข้อมูลรูปแบบปีพุทธศักราช (พ.ศ.) และปีงบประมาณได้ | Heat map + calendar filters — **plus** scheduled heat-map / aging digests | Better | Proposal 5.4, 9 |
| 5.6.2 ข้อกาหนดซอฟต์แวร์เสริม: ในกรณีที่ระบบที่นาเสนอจาเป็นต้องใช้เครื่องมือวิเคราะห์ข้อมูลภายนอก (เช่น Business Intelligence Tool) เพื่อให้สามารถแสดงผลแบบเจาะลึก (Drill-down) ได้อย่างอิสระ ผู้รับจ้างจะต้องเป็นผู้รับผิดชอบค่าใช้จ่ายของสิทธิ์การใช้งาน (License) ซอฟต์แวร์เสริมดังกล่าว ให้ครอบคลุมตามจานวนผู้ใช้งานทั้งหมดของโครงการ | Native default; BI only if BRD requires — Rocket-funded | Equal / note | Proposal 5.4 |
| 5.7.1 ระบบ Single Sign-On (SSO) เพื่อการยืนยันตัวตน (Authentication) และการดึงข้อมูลพื้นฐาน (Master Profile) | Sign in with SSO EECO | Equal | Proposal 5.5 |
| 5.7.2 ระบบบริการ EEC OSS เพื่อดาเนินการดึงข้อมูล (Pull) สถานะการของบริการมาแสดงผล โดยผู้รับจ้างต้องกาหนดขอบเขต Endpoint API ให้ชัดเจนร่วมกับ สกพอ. ในขั้นตอนการวิเคราะห์ระบบ | OSS status panel; endpoints in BA | Equal | Proposal 5.3, 5.5 |
| 5.8.1 การควบคุมการเข้าถึงข้อมูล (Access Control) ต้องมีระบบการกาหนดสิทธิ์การเข้าถึงข้อมูลแบบแบ่งลาดับชั้น (Role-Based Access Control) โดยยึดหลักความจาเป็นในการรับรู้ (Need-to-know basis) โดยเฉพาะเอกสารที่มีชั้นความลับสูง (เช่น หนังสือแสดงเจตจานง (LOI) ข้อตกลงรักษาความลับ (NDA) และงบการเงิน (Financial Statements)) … จากัดสิทธิ์การมองเห็นเฉพาะผู้บริหารระดับสูง หรือผู้ปฏิบัติงานที่เป็นเจ้าของโครงการ (Project Owner) เท่านั้น | Role tiers; sensitive doc class | Equal | Proposal 5.6 |
| 5.8.2 มาตรการรักษาความมั่นคงปลอดภัยของข้อมูล (Data Security Safeguards) … 1) ระบบลายน้า (Dynamic Watermark): ต้องมีระบบประทับลายน้ากึ่งโปร่งใสลงบนเอกสารความลับ … แสดงชื่อบัญชีผู้ใช้งานและวันเวลาที่เรียกดูเอกสารนั้น ๆ ทันทีที่มีการเปิดอ่านหรือดาวน์โหลด 2) การบันทึกประวัติการใช้งานระบบ (Audit Trail & Access Log): ระบบต้องเก็บบันทึกร่องรอยการใช้งานระดับแอปพลิเคชัน (Application Log) อย่างละเอียด … Who / What / When … | Watermark on view/download; app audit log | Equal | Proposal 5.6 |
| 5.8.3 จัด ให้มีการรักษาความปลอดภัยของข้อมูลส่วนบุคคล (PDPA) ของนักลงทุนและผู้ใช้งานทั้งด้านการบริหารจัดการ ( Administrative Safeguard) ด้านเทคนิค (Technical Safeguard) และทางกายภาพ (Physical) ตามมาตรฐานสากลของแต่ละชุดข้อมูล … | Consent + RBAC + logging + guidance | Equal | Proposal 5.1, 5.6 |
| 5.9.1 การทาความสะอาดและตรวจสอบข้อมูล (Data Cleansing & De-duplication): ก่อนการนาเข้าข้อมูล ผู้รับจ้างต้องจัดให้มีพื้นที่พักข้อมูล (Staging Area) เพื่อดาเนินการทาความสะอาดข้อมูลดิบ จัดระเบียบโครงสร้างข้อมูล (Data Mapping) และขจัดข้อมูลที่ซ้าซ้อนกัน โดยอ้างอิงจากเลขประจาตัวผู้เสียภาษี (Tax ID) หรือชื่อนิติบุคคล | Staging → cleanse → dedupe pipeline | Equal | Proposal 5.7 |
| 5.9.2 เงื่อนไขการส่งมอบฐานข้อมูล: เมื่อส่งมอบงาน ฐานข้อมูลในระบบจะต้องอยู่ในสภาพที่สมบูรณ์ เป็นโครงสร้างมาตรฐาน (Structured Data) ไม่มีความซ้าซ้อน และต้องสามารถรองรับ ความสัมพันธ์ของข้อมูล แบบหนึ่งต่อหลายรายการ (One-to-Many) ได้อย่างถูกต้อง เช่น กรณีผู้ติดต่อ 1 ราย มีสถานะเป็นตัวแทนของหลายนิติบุคคล … | Handover condition | Equal | Proposal 5.7, 6 |
| 5.9.3 การจัดการข้อมูลและการเข้าถึง — • เก็บ Log File การใช้งานระบบตามที่กฎหมายกาหนด • บันทึกประวัติการเข้าใช้งานของผู้ใช้ (User Access Log) อย่างน้อย 180 วัน • History Log ต้องสามารถตรวจสอบย้อนหลังได้ และมีมาตรการป้องกันการแก้ไขหรือปลอมแปลงข้อมูล • จัดทาระบบสารองข้อมูล (Data Backup) และแผนกู้คืนระบบ (Disaster Recovery Plan) • กาหนดสิทธิ์การเข้าถึงข้อมูลตามระดับความสาคัญ (Role-based Access Control, RBAC) | Implemented and documented | Equal | Proposal 5.6–5.7, 6 |
