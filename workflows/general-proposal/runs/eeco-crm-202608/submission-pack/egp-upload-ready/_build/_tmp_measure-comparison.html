เอกสารประกอบการยื่นข้อเสนอ · เลขที่โครงการ 69079202016
เอกสารประกวดราคาอิเล็กทรอนิกส์ เลขที่ ๐๑๘/๒๕๖๙ · วันเสนอราคา ๗ สิงหาคม ๒๕๖๙

ตารางเปรียบเทียบคุณลักษณะเฉพาะและข้อกำหนด

ผู้ยื่นข้อเสนอ: บริษัท ร็อคเก็ต อินโนเวชั่น จำกัด · อ้างอิง TOR ข้อ ๑๐.๒ (๖) · หน้า 1/1
คุณลักษณะเฉพาะและข้อกำหนดที่หน่วยงานกำหนด คุณสมบัติที่ผู้ยื่นข้อเสนอนำเสนอ เปรียบเทียบ เอกสารอ้างอิง
3.1 กลุ่มผู้ใช้งาน เจ้าหน้าที่และผู้บริหารของ สกพอ. ตั้งแต่ระดับปฏิบัติการไปจนถึงระดับผู้บริหารระดับสูง ทั้งนี้ ระบบต้องสามารถรองรับผู้ใช้งานแบบระบุตัวตน (Named Users) ได้รวมจานวนไม่น้อยกว่า 100 บัญชี โดยระบบจะต้องได้รับการออกแบบให้สามารถขยายจานวนบัญชีผู้ใช้งานเพิ่มเติมได้ในอนาคต ระบบ CRM รองรับ Named Users ไม่น้อยกว่า 100 บัญชี และขยายจำนวนบัญชีและบทบาทได้ เท่ากัน ข้อเสนอฯ 2, 4
3.2 การรองรับการปฏิบัติงานนอกสถานที่: ระบบต้องถูกออกแบบให้รองรับการใช้งานผ่านอุปกรณ์เคลื่อนที่ (Mobile/Tablet Friendly) และสามารถเข้าถึงผ่านเครือข่ายอินเทอร์เน็ตจากภายนอกสานักงานหรือจากต่างประเทศได้ … โดยระบบต้องมีมาตรฐานการรักษาความมั่นคงปลอดภัยขั้นสูงรองรับ หน้าจอแบบ Responsive บน Next.js รองรับเดสก์ท็อปและแท็บเล็ต เข้าถึงผ่าน HTTPS พร้อม SSO, RBAC, Dynamic Watermark และ Audit Trail เท่ากัน ข้อเสนอฯ 2, 4, 5.2, 5.6
5.1 จัดทาแผนการดาเนินงาน (Project Plan) โดยแผนการดาเนินงานดังกล่าวต้องประกอบด้วยระยะเวลาดาเนินงานและรายชื่อบุคลากรในโครงการ โดยครอบคลุมทุกขั้นตอนของโครงการ รวมถึงการติดตั้ง จัดทำ Project Plan พร้อมกำหนดการ บุคลากรทุกตำแหน่ง ขั้นตอนพัฒนา ทดสอบ โอนย้าย ติดตั้ง และส่งมอบ เท่ากัน ข้อเสนอฯ 6
5.2 การศึกษาและวิเคราะห์ความต้องการ (Business Analysis) ผู้รับจ้างต้องดาเนินการรวบรวม ศึกษา และวิเคราะห์ความต้องการของผู้ใช้งาน (User Requirements) จากผู้บริหารและเจ้าหน้าที่ … เพื่อนามาจัดทาเอกสารความต้องการของระบบ (Business Requirement Document: BRD) โดยต้องนาเสนอกระบวนการทางาน (Workflow) ที่สอดคล้องกับนโยบายการบูรณาการข้อมูล (Centralized Intelligence) บริษัทฯ จะรวบรวมและวิเคราะห์ความต้องการจากผู้บริหารและเจ้าหน้าที่ แล้วจัดทำ BRD พร้อม Workflow ของ Investment Journey และ Ticket ในเฟสที่ 1 เท่ากัน ข้อเสนอฯ 3, 5.3, 6
5.3.1 รวบรวมโครงสร้างข้อมูลเดิม (Data Schema) จากทุกสานักที่เกี่ยวข้อง เพื่อใช้เป็นข้อมูลตั้งต้นสาหรับการโอนย้ายข้อมูล รวบรวม Schema ก่อนจัด Data Mapping สำหรับการโอนย้าย เท่ากัน ข้อเสนอฯ 4.5, 5.7
5.3.2 จัดทาเอกสารการออกแบบระบบ (System Design Document) ส่งมอบ SDD ในเฟสที่ 1 เท่ากัน ข้อเสนอฯ 4, 6
5.3.3 แผนภาพความสัมพันธ์ของข้อมูล (Entity-Relationship Diagram: ER Diagram) หรือเอกสารเทียบเท่าที่อธิบายโครงสร้างความสัมพันธ์ ของข้อมูลได้ (ในกรณีที่เสนอระบบแบบ SaaS) ERD เชิงแนวคิดในข้อเสนอฯ; ERD ฉบับทางการในเฟสที่ 1 เท่ากัน ข้อเสนอฯ 4.3, 4.5
5.3.4 ออกแบบหน้าจอผู้ใช้งาน (User Interface/ User Experience Design) โดยออกแบบในลักษณะหน้าจอแสดงผลกราฟิก ( Graphic User Interface) ที่มีแบบฟอร์ม (Form-based) และปุ่มคาสั่ง (Button Control) ที่ชัดเจน ใช้งานง่าย รองรับการแสดงผลบนอุปกรณ์พกพาเพื่อลดระยะเวลาในการเรียนรู้ระบบของเจ้าหน้าที่ หน้าจอแบบฟอร์มสำหรับ Activity, Task, Ticket และ Investment Case พัฒนาด้วย Next.js และรองรับอุปกรณ์เคลื่อนที่ เท่ากัน ข้อเสนอฯ 4, 5.2, 5.3
5.3.5 ออกแบบระบบ (System Design) โดยระบุ สภาพแวดล้อมของระบบ (System Environment) บริษัทฯ จะระบุ Application stack และสภาพแวดล้อมของระบบ โดยติดตั้ง Production บนคลาวด์ที่ สกพอ. จัดหา และบริหารสภาพแวดล้อม Non-production กับ POC เท่ากัน ข้อเสนอฯ 3, 4
5.3.6 ออกแบบการเชื่อมต่อระบบ (Integration Scope) และกาหนดการเชื่อมต่อระบบ (API Interface Document) สาหรับระบบ EEC OSS บริษัทฯ จะจัดทำ API Interface Document ร่วมกับ สกพอ. และเชื่อมต่อเพื่อแสดงสถานะ EEC OSS บน Investment Case เท่ากัน ข้อเสนอฯ 5.5
5.3.7 จัดทาเอกสารแสดงรายละเอียดคุณสมบัติของโครงสร้างพื้นฐาน ประกอบด้วย ระบบฐานข้อมูล (Database) เครือข่าย (Network) และสถาปัตยกรรมระบบ (System Architecture) พร้อมทั้งกาหนดคุณสมบัติขั้นต่าของโครงสร้างพื้นฐานที่ผู้ว่าจ้างต้องจัดเตรียมให้เพียงพอต่อการใช้งานในวงกว้าง (Production) โดย สกพอ. จะประสานงานกับผู้ให้บริการ Cloud เช่น GDCC เพื่อจัดหาเครื่องแม่ข่ายต่อไป บริษัทฯ จะจัดทำคุณสมบัติขั้นต่ำด้านฐานข้อมูล เครือข่าย และสถาปัตยกรรมแบบไม่ผูก Vendor พร้อมติดตั้งและตั้งค่าระบบบนโฮสต์ที่ สกพอ. จัดหา เท่ากัน ข้อเสนอฯ 3, 4, 6
5.4 การประเมินความเสี่ยง ผลกระทบ และการปรับปรุงแก้ไขเพื่อรองรับการทางานร่วมกับระบบต่าง ๆ ภายในของ สกพอ. ที่เกี่ยวข้อง เช่น ระบบบริการ EEC OSS ซึ่งให้บริการด้านเขตส่งเสริมเศรษฐกิจพิเศษ ด้านสิทธิประโยชน์ ด้านอนุมัติ อนุญาต และด้านการให้คาปรึกษา เป็นต้น ประเมินความเสี่ยงและผลกระทบต่อ EEC OSS และระบบที่เกี่ยวข้อง พร้อมกำหนดแนวทางแก้ไขในเฟสที่ 1 เท่ากัน ข้อเสนอฯ 5.5, 6
5.5.1 การรับ/ป้อนข้อมูล (Data Capture) — 1) …รองรับการบันทึกแหล่งข้อมูลที่ได้รับมาจากหลากหลายช่องทาง เช่น โซเชียลมีเดีย (LINE OA, Facebook Messenger) อีเมล และ Call Center เป็นต้น 2) รองรับการนาเข้าและส่งออกข้อมูลจานวนมาก (Bulk Upload) ผ่านไฟล์มาตรฐาน เช่น CSV, Excel พร้อมระบบตรวจสอบความถูกต้องของข้อมูลเบื้องต้น (Data Validation) บันทึกแหล่งที่มาจาก LINE OA, Facebook Messenger, อีเมล และ Call Center พร้อมนำเข้า CSV/Excel ผ่านการตรวจสอบฟิลด์บังคับ รูปแบบ และข้อมูลซ้ำ เท่ากัน ข้อเสนอฯ 5.1
5.5.2 การจัดเก็บและบริหารข้อมูล (Data Management) — 1) หน้าจอแสดงข้อมูลลูกค้าแบบศูนย์รวม (Single Source of Truth) … 2) …ชุดข้อมูล (Master Data) … 3) …ระบบให้คะแนน (Lead Scoring) … 4) รองรับการตรวจสอบและจัดการข้อมูลซ้าซ้อนโดยอัตโนมัติ … 5) …บันทึกประวัติการให้ความยินยอม (Consent) …ตาม พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล Customer 360 แสดง Master Data, Lead Scoring และประวัติ Consent พร้อมตรวจข้อมูลซ้ำด้วย Tax ID และชื่อนิติบุคคล — เพิ่ม หน้าจอรวมข้อมูลซ้ำแบบมีผู้ใช้ตรวจสอบก่อนยืนยันการรวม ดีกว่า ข้อเสนอฯ 5.1, 9
5.5.3 การบริหารความสัมพันธ์ (Relationship & Activity Management) — 1) สามารถบันทึกปฏิสัมพันธ์การให้บริการ ติดตาม และกิจกรรมที่เกี่ยวข้องกับนักลงทุน (Interaction & Activity Tracking) … Timeline … รองรับการใช้งานผ่านอุปกรณ์พกพา (Mobile/Tablet) … 2) ระบบจัดการงานและปฏิทินนัดหมาย (Task & Calendar Management) … 3) ระบบออกเลขรับเรื่อง (Ticket Management) … SLA Tracking … Escalate … บันทึก Activity พร้อมไฟล์แนบ จัดการ Task และปฏิทิน และเปิด Ticket พร้อมการมอบหมายและ SLA — เพิ่ม คิวบันทึกงานภาคสนามเมื่อออฟไลน์ และหน้าจอกำหนดเส้นทางการส่งต่อรายสำนัก ดีกว่า ข้อเสนอฯ 5.2, 9
5.5.4 การติดตามสถานะ (Pipeline / Workflow Management) — 1) ระบบต้องสามารถติดตามสถานะของนักลงทุน หรือโครงการลงทุน ในรูปแบบ Pipeline หรือ Workflow โดยสามารถกาหนดขั้นตอน (Stage) และเงื่อนไขการเปลี่ยนสถานะได้ รวมถึงสามารถแสดงความคืบหน้าของแต่ละรายการได้อย่างชัดเจน 2) รองรับ ระบบติดตามและแจ้งเตือนระยะเวลามาตรฐานการให้บริการ (Service Level Agreement) เปิด Investment Case บน Pipeline ย้าย Stage ตามเส้นทางและ Checklist ที่กำหนด พร้อม Stage SLA และประวัติการเปลี่ยนสถานะ — เพิ่ม คลังเทมเพลต Journey สำหรับ FDI การลงทุนในประเทศ และ Aftercare ดีกว่า ข้อเสนอฯ 5.3, 9
5.5.5 รายงานและวิเคราะห์ (Reporting & Analytics) — 1) ระบบต้องสามารถจัด ท ารายงานและวิเคราะห์ข้อมูล (Reporting & Analytics) โดยรองรับการแสดงผลในรูปแบบ Dashboard และสามารถปรับแต่งรายงานได้ เช่น รายงานตามประเทศ อุตสาหกรรม มูลค่าการลงทุน เป็นต้น 2) สามารถส่งออกข้อมูลในรูปแบบ excel หรือ PDF ได้เป็นอย่างน้อย เป็นต้น Dashboard และ Heat Map ใช้ข้อมูลจาก Case และ Ticket ชุดเดียวกัน รองรับรายงานตามประเทศ อุตสาหกรรม และมูลค่าการลงทุน พร้อมส่งออก Excel/PDF — เพิ่ม รายงานสรุปสำหรับผู้บริหารตามรอบเวลา ดีกว่า ข้อเสนอฯ 5.4, 9
5.5.6 การเชื่อมโยงข้อมูล (Integration & Data Sharing) — 1) ระบบต้องสามารถเชื่อมโยงและแลกเปลี่ยนข้อมูลกับระบบอื่น (System Integration) ผ่าน API … โดยเชื่อมกับระบบ SSO EECO และ EEC OSS ของ สกพอ. เป็นต้น 2) รองรับการเชื่อมต่อข้อมูลผ่าน Open API (RESTful API / SOAP) เพื่อความยืดหยุ่นในการขยายระบบในอนาคต ระบบจะยืนยันตัวตนผ่าน SSO EECO และดึงสถานะ EEC OSS มาแสดงบน Investment Case โดยใช้ REST เป็นหลักและรองรับ SOAP เมื่อระบบปลายทางกำหนด เท่ากัน ข้อเสนอฯ 5.5
5.6.1 การกรองข้อมูล (Data Filtering): ระบบต้องสามารถแสดงผลภาพรวมภาระงาน (Heat Map) และต้องสามารถกรองข้อมูลรูปแบบปีพุทธศักราช (พ.ศ.) และปีงบประมาณได้ Heat Map แสดงภาระงานและรายการเสี่ยง SLA พร้อมตัวกรองปี พ.ศ. และปีงบประมาณ เท่ากัน ข้อเสนอฯ 5.4
5.6.2 ข้อกาหนดซอฟต์แวร์เสริม: ในกรณีที่ระบบที่นาเสนอจาเป็นต้องใช้เครื่องมือวิเคราะห์ข้อมูลภายนอก (เช่น Business Intelligence Tool) เพื่อให้สามารถแสดงผลแบบเจาะลึก (Drill-down) ได้อย่างอิสระ ผู้รับจ้างจะต้องเป็นผู้รับผิดชอบค่าใช้จ่ายของสิทธิ์การใช้งาน (License) ซอฟต์แวร์เสริมดังกล่าว ให้ครอบคลุมตามจานวนผู้ใช้งานทั้งหมดของโครงการ ใช้ Dashboard ในระบบเป็นค่าเริ่มต้น หาก BRD ระบุว่าต้องใช้เครื่องมือ BI ภายนอก บริษัทฯ จะรับผิดชอบค่า License สำหรับผู้ใช้งานโครงการทั้งหมด เท่ากัน ข้อเสนอฯ 5.4
5.7.1 ระบบ Single Sign-On (SSO) เพื่อการยืนยันตัวตน (Authentication) และการดึงข้อมูลพื้นฐาน (Master Profile) เข้าสู่ระบบด้วย SSO EECO เท่ากัน ข้อเสนอฯ 5.5
5.7.2 ระบบบริการ EEC OSS เพื่อดาเนินการดึงข้อมูล (Pull) สถานะการของบริการมาแสดงผล โดยผู้รับจ้างต้องกาหนดขอบเขต Endpoint API ให้ชัดเจนร่วมกับ สกพอ. ในขั้นตอนการวิเคราะห์ระบบ แสดงสถานะ EEC OSS บน Investment Case และกำหนดขอบเขต Endpoint ร่วมกับ สกพอ. ในขั้นวิเคราะห์ความต้องการ เท่ากัน ข้อเสนอฯ 5.3, 5.5
5.8.1 การควบคุมการเข้าถึงข้อมูล (Access Control) ต้องมีระบบการกาหนดสิทธิ์การเข้าถึงข้อมูลแบบแบ่งลาดับชั้น (Role-Based Access Control) โดยยึดหลักความจาเป็นในการรับรู้ (Need-to-know basis) โดยเฉพาะเอกสารที่มีชั้นความลับสูง (เช่น หนังสือแสดงเจตจานง (LOI) ข้อตกลงรักษาความลับ (NDA) และงบการเงิน (Financial Statements)) … จากัดสิทธิ์การมองเห็นเฉพาะผู้บริหารระดับสูง หรือผู้ปฏิบัติงานที่เป็นเจ้าของโครงการ (Project Owner) เท่านั้น ระบบจะกำหนดสิทธิ์ตามบทบาทและชั้นความลับ โดยจำกัด LOI, NDA และงบการเงินตามหลัก Need-to-know ให้เฉพาะผู้บริหารหรือเจ้าของโครงการที่ได้รับอนุญาต เท่ากัน ข้อเสนอฯ 5.6
5.8.2 มาตรการรักษาความมั่นคงปลอดภัยของข้อมูล (Data Security Safeguards) … 1) ระบบลายน้า (Dynamic Watermark): ต้องมีระบบประทับลายน้ากึ่งโปร่งใสลงบนเอกสารความลับ … แสดงชื่อบัญชีผู้ใช้งานและวันเวลาที่เรียกดูเอกสารนั้น ๆ ทันทีที่มีการเปิดอ่านหรือดาวน์โหลด 2) การบันทึกประวัติการใช้งานระบบ (Audit Trail & Access Log): ระบบต้องเก็บบันทึกร่องรอยการใช้งานระดับแอปพลิเคชัน (Application Log) อย่างละเอียด … Who / What / When … ระบบจะประทับ Dynamic Watermark ที่ระบุชื่อบัญชีและเวลาเมื่อเปิดดูหรือดาวน์โหลดเอกสารลับ พร้อมบันทึกผู้ใช้ การกระทำ และเวลาใน Application Audit Log เท่ากัน ข้อเสนอฯ 5.6
5.8.3 จัด ให้มีการรักษาความปลอดภัยของข้อมูลส่วนบุคคล (PDPA) ของนักลงทุนและผู้ใช้งานทั้งด้านการบริหารจัดการ ( Administrative Safeguard) ด้านเทคนิค (Technical Safeguard) และทางกายภาพ (Physical) ตามมาตรฐานสากลของแต่ละชุดข้อมูล … บันทึก Consent บังคับสิทธิ์ด้วย RBAC และเก็บ Audit Log พร้อมจัดทำแนวทางมาตรการด้านการบริหาร เทคนิค และกายภาพร่วมกับ สกพอ. เท่ากัน ข้อเสนอฯ 4.4, 5.1, 5.6
5.9.1 การทาความสะอาดและตรวจสอบข้อมูล (Data Cleansing & De-duplication): ก่อนการนาเข้าข้อมูล ผู้รับจ้างต้องจัดให้มีพื้นที่พักข้อมูล (Staging Area) เพื่อดาเนินการทาความสะอาดข้อมูลดิบ จัดระเบียบโครงสร้างข้อมูล (Data Mapping) และขจัดข้อมูลที่ซ้าซ้อนกัน โดยอ้างอิงจากเลขประจาตัวผู้เสียภาษี (Tax ID) หรือชื่อนิติบุคคล พักข้อมูลใน Staging ตรวจสอบและปรับรูปแบบ จัดทำ Data Mapping ขจัดข้อมูลซ้ำด้วย Tax ID หรือชื่อนิติบุคคล แล้วจึงโหลดข้อมูลที่ผ่านการตรวจสอบ เท่ากัน ข้อเสนอฯ 5.7
5.9.2 เงื่อนไขการส่งมอบฐานข้อมูล: เมื่อส่งมอบงาน ฐานข้อมูลในระบบจะต้องอยู่ในสภาพที่สมบูรณ์ เป็นโครงสร้างมาตรฐาน (Structured Data) ไม่มีความซ้าซ้อน และต้องสามารถรองรับ ความสัมพันธ์ของข้อมูล แบบหนึ่งต่อหลายรายการ (One-to-Many) ได้อย่างถูกต้อง เช่น กรณีผู้ติดต่อ 1 ราย มีสถานะเป็นตัวแทนของหลายนิติบุคคล … ส่งมอบฐานข้อมูลแบบ Structured Data ที่ลดข้อมูลซ้ำและรองรับผู้ติดต่อ 1 รายต่อหลายนิติบุคคล เท่ากัน ข้อเสนอฯ 5.7, 6
5.9.3 การจัดการข้อมูลและการเข้าถึง — • เก็บ Log File การใช้งานระบบตามที่กฎหมายกาหนด • บันทึกประวัติการเข้าใช้งานของผู้ใช้ (User Access Log) อย่างน้อย 180 วัน • History Log ต้องสามารถตรวจสอบย้อนหลังได้ และมีมาตรการป้องกันการแก้ไขหรือปลอมแปลงข้อมูล • จัดทาระบบสารองข้อมูล (Data Backup) และแผนกู้คืนระบบ (Disaster Recovery Plan) • กาหนดสิทธิ์การเข้าถึงข้อมูลตามระดับความสาคัญ (Role-based Access Control, RBAC) เก็บ Application Log และ User Access Log อย่างน้อย 180 วันแบบตรวจสอบย้อนหลังได้ จัดทำ Backup/DR และบังคับสิทธิ์ด้วย RBAC เท่ากัน ข้อเสนอฯ 5.6–5.7, 6
5.10.1 ดาเนินการทดสอบการยอมรับระบบ (User Acceptance Test: UAT) ร่วมกับเจ้าหน้าที่ สกพอ. ดำเนิน UAT ร่วมกับเจ้าหน้าที่ สกพอ. ในเฟสที่ 2 พร้อมบันทึกผลและแก้ไขข้อค้นพบก่อนตรวจรับ เท่ากัน ข้อเสนอฯ 6.3
5.10.2 การพัฒนาระบบและความปลอดภัย — • พัฒนาระบบตามมาตรฐาน OWASP (Open Web Application Security Project) เวอร์ชั่นล่าสุด • ให้บริการผ่าน SSL Certificate ของ สกพอ. สาหรับการเข้ารหัสข้อมูล บริษัทฯ จะพัฒนาระบบตามแนวทาง OWASP เวอร์ชันปัจจุบัน และให้บริการ Production ผ่าน SSL Certificate ที่ สกพอ. จัดเตรียม เท่ากัน ข้อเสนอฯ 5.6
