# Project-proof stretch methodology

How to select and present past-work evidence from `resources/project-proofs/` for a new bid.

## Purpose

- Review the canonical library against TOR past-work rules (value floors, recency, domain keywords).
- Feedback which proofs are **usable**, **stretchable**, or **insufficient**.
- Pull selected PDFs into the run pack.
- AI-generate a **cover summary** (name, amount, open scope) that is relevant to the bid without inventing false facts.

## Assessment (dossier / plan — not customer prose)

For each library proof, record:

| Field | Meaning |
|---|---|
| Meets hard gates? | Value, date, counterparty type, certificate present |
| Domain fit | Strong / stretchable / weak |
| Stretch framing | One-line open scope that stays honest |
| Use in this bid? | Lead / count filler / out |

**Stretchable** means the signed evidence does not lock you into a narrow product label (e.g. “loyalty”) and can be described as CRM / work-tracking / B2B relationship management in ways the contract pages do not contradict.

## Cover-writing rules (customer-facing)

1. Include **client/legal name**, **contract value** (prefer certificate figures when image totals disagree), and **scope**.
2. Scope should be **open and relevant** to the bid category — not a loyalty brochure dump, not empty fluff.
3. Prefer vague operational language: users/sales managing counterparties; mall users managing stores/tenants and documents; central CRM for customers and related parties.
4. Do **not** invent modules, integrations, or outcomes absent from evidence.
5. Do **not** over-specify details an owner could dispute from the contract face.
6. Sole contractor vs JV: state what the certificate/contracts show — do not leave TOR checkboxes blank if status is known.

### Framing examples (patterns — rewrite per bid)

| Library proof | Over-narrow (avoid on B2B gov CRM) | Open-but-usable |
|---|---|---|
| Syngenta | “Loyalty program for growers” | CRM for internal users and sales to manage counterparties / related parties, track activities and service through a central database |
| Future Park (Rangsit) | “Mall loyalty program” | CRM for mall users and management to manage stores/tenants and related parties, track work status and documents through a central database |
| B2C loyalty contracts | Long loyalty feature list | Central CRM for customer relationship management (when TOR accepts CRM/work-tracking generally) |

## Procedure

1. Read TOR past-work clauses (verbatim).
2. Open `project-proofs/INDEX.md` + PDFs as needed.
3. Assess each proof; persist table in dossier / outline evidence plan.
4. If library insufficient → feedback in `manual-requests.md` (need new evidence).
5. After picks locked → **Late AI** cover PDF/MD → combine with certificate + contracts into pack.
6. Face-check scans before upload (image PDFs often have no extractable text).
