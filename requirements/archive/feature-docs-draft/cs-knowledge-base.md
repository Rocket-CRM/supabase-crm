# Feature Guide: CS Knowledge Base

## 1. Overview

The Knowledge Base is the central content repository for the CS module's AI agent. It stores articles — product descriptions, policies, FAQs, how-to guides — that both the AI agent and human agents reference when answering customer questions. Without knowledge base content, the AI has nothing to ground its responses on and cannot answer domain-specific questions.

Content enters the knowledge base through two paths: manually authored articles (written directly in the admin editor) and synced sources (documents, website crawls, catalog imports, API feeds). When an article is created or updated, an automatic embedding pipeline chunks the text into ~500-token segments, generates vector embeddings via OpenAI, and stores them in pgvector. This enables the AI agent to perform semantic search — finding relevant knowledge even when the customer's phrasing doesn't match the article's exact wording.

A separate feature, Custom Answers, lets admins define exact responses for specific question patterns. These override AI-generated responses and are checked before the AI reasons over retrieved knowledge. Custom answers are stored as a special type of knowledge article (`is_custom_answer = true`) with trigger patterns that match against incoming messages.

## 2. Key Concepts

**Knowledge Article** — A unit of content in the knowledge base: a title, rich-text body, category, language, and status. Articles are the atomic unit that gets embedded and searched. Example: "Return Policy — Thailand" with content explaining the 7-day return window.

**Knowledge Source** — A content feed that produces articles. Sources have a type (document, website, catalog, API, manual), sync configuration, and sync status. Example: A "Product FAQ Website" source of type `url` that crawls the brand's FAQ page.

**Source Type** — How content enters the system. Five types: `document` (uploaded PDF/DOCX/TXT/CSV), `url` (website crawler), `catalog` (product catalog sync from Shopee/Lazada/Shopify), `api` (external CMS connector), `manual` (hand-written in admin editor).

**Sync Status** — Tracks whether a source's content is current. Values: `pending` (never synced), `syncing` (sync in progress), `synced` (up to date), `failed` (last sync errored). Each source tracks `last_synced_at` and `article_count`.

**Category** — Organizational grouping for articles. Default categories: `products`, `policies`, `shipping`, `returns`, `faq`. Displayed as filter chips in the admin article list.

**Article Status** — Lifecycle state controlling searchability. Values: `draft` (being written, not searchable), `active` (searchable by AI and agents), `archived` (hidden from search, retained for history). Default for new articles: `draft`.

**Embedding** — A 1536-dimensional vector representation of a text chunk, generated by OpenAI's text-embedding model. Stored in pgvector. Used for semantic similarity search — finding content by meaning rather than exact keyword match.

**Chunk** — A ~500-token segment of an article's content. Long articles are split into multiple chunks, each independently embedded. The `chunk_index` tracks ordering within the article.

**Semantic Search** — How the AI agent finds relevant knowledge. The customer's question is embedded into a vector, then compared against all stored chunk embeddings using cosine similarity. Returns the top K most relevant chunks above a similarity threshold (default 0.7).

**Text Search** — How human agents find knowledge during conversations. Uses text matching (ILIKE) against article titles and content. Simpler than semantic search but works without embeddings.

**Custom Answer** — An article with `is_custom_answer = true` that includes `question_patterns` (trigger phrases). When a customer message contains any trigger phrase (case-insensitive LIKE match), the custom answer's content is used directly instead of AI-generated reasoning. Higher `priority` values are checked first.

**Question Patterns** — A text array on custom answer articles. Each entry is a phrase that, when found in a customer message (substring match, case-insensitive), triggers the custom answer. Example: `["return policy", "how to return", "refund process"]`.

**Embedding Pipeline** — The automatic process that converts article text into searchable vectors. Triggered on article insert or update via DB trigger → pgmq queue → pg_cron → Edge Function (`embed-knowledge`) → OpenAI API → pgvector storage. On update, old chunks are deleted and regenerated.

## 3. Configuration Reference

### Article Settings

| Setting | What it controls | Options / Example | Default |
|---|---|---|---|
| Title | Article display name, searched by text search | "How to Return a Product" | Required |
| Content | Rich-text body, chunked and embedded for AI search | HTML content | Empty |
| Status | Searchability by AI and agents | `draft`, `active`, `archived` | `draft` |
| Category | Organizational grouping and filter | `products`, `policies`, `shipping`, `returns`, `faq` | None |
| Language | Content language tag | `en`, `th`, `ja`, `zh` | `en` |

### Custom Answer Settings

| Setting | What it controls | Options / Example | Default |
|---|---|---|---|
| Is Custom Answer | Marks article as exact-response override | `true` / `false` | `false` |
| Question Patterns | Trigger phrases that activate this answer | `["return policy", "how to return"]` | `[]` |
| Priority | Ordering when multiple custom answers match | Higher = checked first | `0` |

### Source Settings

| Setting | What it controls | Options / Example | Default |
|---|---|---|---|
| Name | Display label for the source | "Product FAQ Website" | Required |
| Source Type | Content ingestion method | `document`, `url`, `catalog`, `api`, `manual` | Required |
| Config | Type-specific configuration (JSONB) | URL, credentials, sync schedule | `{}` |
| Is Active | Whether sync is enabled | `true` / `false` | `true` |

### 4a. Knowledge Hub Dashboard

1. **Knowledge Hub** is the landing page — shows four stat cards: Sources count, Articles count, Custom Answers count, Active/Draft breakdown
2. Below stats: **Knowledge Sources** card listing each source with name, type badge, sync status badge, article count, and last synced date
3. Warning banner appears if any sources have `sync_status = failed`
4. Two side-by-side cards: **Recent Articles** (5 most recent non-custom-answer articles) and **Custom Answers** (5 most recent)
5. Primary action button: **"New article"**. Secondary actions: **"Add source"**, **"New custom answer"**

### 4b. Create an Article

1. From **Knowledge Hub**, click **"New article"** (or from **Article List**, click create)
2. **Article Editor** opens — main area: Title (required) + rich-text Content editor
3. Sidebar: Status dropdown (draft/active/archived), Category dropdown, Language dropdown
4. Click **"Publish article"** to save
5. On save: triggers embedding pipeline automatically if status is `active`

### 4c. Manage Articles

1. **Article List** displays articles with title, category badge, status badge
2. Filter by: search text, category, source, status
3. Click any article row → opens **Article Editor** in edit mode
4. Edit mode shows additional Details card: source type, created date, updated date
5. Secondary action toggles between "Activate" and "Revert to draft"
6. Delete available from the list view

### 4d. Manage Sources

1. **Source List** shows all sources with name, type badge (Document/Website/Catalog/API/Manual), sync status badge (Synced/Syncing/Pending/Failed), article count, and last synced timestamp
2. Click **"Add source"** → **Source Editor**: name (required), source type dropdown, config JSONB (type-specific — URL for website sources, file path for documents), active toggle
3. Each source can be individually synced via **trigger sync** action
4. Failed sources show in the **Knowledge Hub** warning banner with source names and "View sources" link
5. Deactivating a source (`is_active = false`) stops future syncs but does not remove existing articles

### 4e. Manage Custom Answers

1. **Custom Answer List** shows answers with title, trigger pattern count, and priority value
2. Create flow similar to articles but with additional fields: question patterns (text array of trigger phrases), priority (integer, higher = checked first)
3. Custom answers require at least one question pattern (BFF validation rejects empty arrays)
4. Edit mode shows same fields as creation, pre-populated from stored data

### 4f. Common Admin Mistakes

- Creating articles but leaving them as `draft` → AI cannot find them, support quality drops
- Setting up a source but not triggering initial sync → zero articles imported
- Writing custom answers with overly broad patterns (e.g., `"order"`) → matches unrelated questions
- Writing custom answers with overly narrow patterns → customers phrase questions differently, answer never triggers
- Archiving articles still referenced by active procedures → procedure context becomes incomplete
- Ignoring failed source sync warnings → knowledge becomes stale without admin realizing

## 5. Agent / AI Experience

This feature has no direct customer-facing UI. Knowledge is consumed by AI and human agents as reference material.

**Route map (agent-facing, within CS Inbox):**

| Context | Access point | Data source |
|---|---|---|
| AI semantic search | Automatic during AI response generation | `cs_fn_search_knowledge(embedding, limit, category, threshold)` |
| AI custom answer check | Automatic before AI generates response | `cs_fn_match_custom_answer(merchant_id, message_text)` |
| Human agent sidebar search | Search box in conversation sidebar | `cs_bff_search_conversation_knowledge(search_text, category, limit)` |

### 5a. AI Agent Uses Knowledge

1. Customer sends a message
2. System checks for custom answer match first: `cs_fn_match_custom_answer` runs LIKE matching against active custom answers' `question_patterns`, ordered by `priority` DESC
3. If custom answer matches → its content is used directly as the response (no AI reasoning)
4. If no custom answer matches → customer message is embedded via OpenAI → `cs_fn_search_knowledge` runs cosine similarity against `cs_knowledge_embeddings` → top K chunks (above 0.7 threshold) returned → injected into LLM prompt as context → AI generates grounded response

### 5b. Human Agent Uses Knowledge

1. During a conversation, agent sees a search box in the sidebar
2. Agent types a query → `cs_bff_search_conversation_knowledge` performs text search against active articles
3. Matching articles displayed with title and content preview
4. Agent reads the article to inform their response to the customer

## 6. Perspectives

### 6a. For CS Managers

**Value:** The knowledge base directly controls AI answer quality. Coverage gaps mean the AI deflects or hallucinates. Well-organized, up-to-date knowledge means higher auto-resolution rates and fewer escalations to human agents.

**Key management tasks:**
- Monitor the Knowledge Hub dashboard for failed source syncs
- Review draft articles and activate them when ready
- Track which categories have thin coverage (few articles) — these are likely escalation hotspots
- Create custom answers for frequently asked questions where the AI's generated response isn't precise enough
- Archive outdated articles after promotions end or policies change

**Custom answers vs articles:** Use articles for general knowledge the AI should reason over. Use custom answers when you need an exact, controlled response — temporary promotions, legal-sensitive policy statements, or questions where AI phrasing is unreliable.

### 6b. For Marketing

**Value:** The knowledge base trains the brand's AI voice. Product descriptions, FAQs, and policy documents feed directly into how the AI represents the brand to customers. Marketing controls brand accuracy by controlling what content exists in the knowledge base.

**Use cases:**
- **Product launches** — Upload product knowledge articles before launch day so the AI can answer questions from day one
- **Campaign-specific FAQs** — Create custom answers for promotion-related questions ("What's the discount code?" → exact answer) with `priority` set high so they override general knowledge
- **Brand consistency** — The AI only knows what's in the knowledge base. Keeping articles current ensures consistent messaging across all customer touchpoints
- **Multi-language support** — Articles tagged by language enable the AI to respond in the customer's language using localized content

### 6c. For Testers

**Config → expected behavior:**

| Config | Expected behavior |
|---|---|
| Article `status = draft` | Not returned by semantic search or text search |
| Article `status = active` | Returned by both search types |
| Article `status = archived` | Not returned by search |
| Custom answer with patterns `["refund"]`, `status = active` | Customer message "How do I get a refund?" → custom answer content used directly |
| Custom answer with `status = draft` | Not matched even if patterns match |
| Two custom answers match, priority 10 vs priority 5 | Priority 10 answer wins |
| Source `sync_status = failed` | Warning banner on Knowledge Hub |
| Source `is_active = false` | Source not synced, existing articles remain |
| Article updated | Old embeddings deleted, new embeddings generated |
| Article deleted | Associated embeddings cascade-deleted |

**Embedding pipeline assertions:**

- ASSERT: New active article → within seconds, `cs_knowledge_embeddings` rows exist for that `article_id`
- ASSERT: Article content updated → old chunks deleted, new chunks with updated content created
- ASSERT: Article deleted → all `cs_knowledge_embeddings` with that `article_id` are gone
- ASSERT: Draft article → no embeddings generated (only active articles are embedded)
- ASSERT: `cs_fn_search_knowledge` with `p_similarity_threshold = 0.7` → only chunks with cosine similarity >= 0.7 returned

**Custom answer matching assertions:**

- ASSERT: `cs_fn_match_custom_answer` uses case-insensitive substring matching (LIKE `%pattern%`)
- ASSERT: Only `is_custom_answer = true` AND `status = 'active'` articles are checked
- ASSERT: Highest `priority` match wins when multiple patterns match
- ASSERT: Returns `NULL` when no patterns match

**Status model (single track):**

| Field | Values | Transition | Effect |
|---|---|---|---|
| `status` | `draft` → `active` | Admin activates | Article becomes searchable, embedding pipeline runs |
| `status` | `active` → `archived` | Admin archives | Article excluded from search, embeddings retained |
| `status` | `active` → `draft` | Admin reverts to draft | Article excluded from search |
| `status` | `archived` → `active` | Admin reactivates | Article searchable again |

**Cross-feature scenarios:**

- Human agent searches knowledge during conversation → results are merchant-scoped (RLS on `merchant_id`)
- Brand A's knowledge never appears in Brand B's search results (multi-tenant isolation)
- Bulk status update (multiple articles → active/draft) via `cs_bff_bulk_update_articles`
- Source sync produces articles → articles automatically get embeddings via pipeline
- Custom answer with empty `question_patterns` → BFF validation rejects save
- Semantic search with no matching content (similarity below threshold for all chunks) → AI falls back to general reasoning or escalates

## 7. Business Rules

**Rule:** Only active articles are searchable. Draft and archived articles exist in the database but are excluded from both semantic search and text search.
**Example:** Admin creates an article about a new return policy but keeps it as `draft` while legal reviews. AI and agents cannot find it until the admin changes status to `active`.

**Rule:** Custom answers are checked before AI reasoning. The system runs `cs_fn_match_custom_answer` first; only if it returns null does the semantic search + LLM pipeline execute.
**Example:** Custom answer exists for "return policy" with priority 10. Customer asks "What's your return policy?" → exact custom answer content returned, AI does not generate its own response.

**Rule:** Custom answer matching uses case-insensitive substring matching (LIKE), not semantic similarity. The customer's message must contain the pattern as a substring.
**Example:** Pattern `"return policy"` matches "What is your return policy?" but does NOT match "How do I send something back?" (even though semantically similar).

**Rule:** On article update, the embedding pipeline deletes all existing chunks and regenerates from the new content. There is no incremental update.
**Example:** Admin edits a 3-chunk article, adding a paragraph. All 3 old chunks are deleted. The updated content is re-chunked (now 4 chunks) and re-embedded.

**Rule:** Knowledge is merchant-scoped. RLS on `merchant_id` ensures Brand A's articles, sources, and embeddings are invisible to Brand B. This applies to all search functions and admin BFFs.
**Example:** Brand A has 200 articles about skincare. Brand B searching for "moisturizer" returns zero results from Brand A's content.

**Rule:** Source `article_count` tracks how many articles were created from that source. Deleting a source does not automatically delete its articles (articles may have been manually edited after sync).
**Example:** Admin deletes the "Product FAQ Website" source. The 50 articles it created remain in the knowledge base.

**Rule:** Custom answers require at least one question pattern. The BFF validates this on save — an empty `question_patterns` array is rejected.
**Example:** Admin tries to save a custom answer with no patterns → error returned, save blocked.
